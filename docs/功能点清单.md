# 家味 · 家庭点餐系统 — 功能点清单

> 清点时间：2026-10-21 · 依据：全部源码通读（backend/src 12 个 Rust 文件、database SQL 与运维工具 8 个脚本、frontend/src 48 个文件）
> 说明：README 描述的是初版功能；实际代码已扩展出「封面图片上传」与「常用功能」四大本地工具（账本 / 经期提醒 / 快递取件码 / 学习），本文以代码为准。

---

## 一、总体架构与部署

| 层 | 技术 | 说明 |
|----|------|------|
| 后端 | Rust 1.75+ · actix-web 4 · sqlx 0.8（MySQL） | 12 个源文件，约 4500 行 |
| 数据库 | MySQL 8.0.16+ | 11 表 + 5 视图 + 2 存储过程，utf8mb4 |
| 前端 | Vue 3.5 · Vite 6 · Pinia · Vue Router 4 · Axios | 无 UI 框架，样式手写；18 个路由页面 |
| 运维 | Node.js · mysql2 | 8 个数据库工具脚本 |

- **一键启动**：`start.bat` 自动装前端依赖 → 构建 → 生成默认 `.env` → `cargo run --release`；未建 `.env` 时用内置默认连接串。
- **单端口部署**：后端托管 `frontend/dist`（仅当目录下存在 `index.html` 才启用），SPA history 路由回退 `index.html`，`/api/*` 未命中返回 JSON 404。
- **多端适配**：前后端监听 `0.0.0.0`，手机（单列 + 底部导航）与平板（多列网格 + 1180px 居中限宽）同一套路由 CSS 自适应；支持 iPhone 安全区。
- **离线演示模式**：前端启动探测 `/api/health`，后端或数据库不可达时自动降级到内存 Mock（15 道示例菜谱、5 成员、4 笔订单），所有页面与交互完整可演示，写操作只改内存、刷新还原；顶部常驻黄色提示条。

## 二、后端功能点（Rust）

### 2.1 基础设施（main.rs / config.rs / db.rs / error.rs / util.rs / dto.rs / models.rs）

1. **配置**：`dotenv` 加载 `.env`，全部项有内置默认值；`DATABASE_URL / HOST / PORT / CORS_ORIGIN / STATIC_DIR（none 关闭托管）/ UPLOAD_DIR / DB_MAX_CONNECTIONS / DB_CONNECT_RETRIES / RUST_LOG`；另预留 `KUAIDI100_KEY / KUAIDI100_CUSTOMER`（快递100 物流轨迹，两项填齐才启用，当前无调用方）。
2. **连接池**：sqlx MySQL 池，启动重试（默认 3 次）、acquire 5s / idle 10min / max_lifetime 30min；池建好即返回，MySQL 后续恢复无需重启后端；`SELECT 1` 主动 ping。
3. **优雅降级**：无池时服务照常启动，数据库接口返回 503 + 配置引导文案（`DB_HINT`）。
4. **CORS**：`*` 任意来源，或逗号分隔白名单（格式校验、非法项告警跳过、白名单为空回退 `*`）。
5. **中间件**：响应压缩、请求日志（`%r -> %s %Dms`）、路径归一化；JSON/Path/Query 错误统一转 400 友好文案；请求体上限 4MB。
6. **worker 数**：`min(4, max(2, CPU 并行度))`。
7. **统一响应**：`{code, message, data}`；错误码 4000/4040/4090/5000/5030；sqlx 错误智能映射——唯一键冲突转「菜名已存在 / 昵称被占用 / 标签已存在 / 订单号冲突」，SQLSTATE 45000（存储过程 SIGNAL）透传业务文案，42S02 引导「先执行建表脚本」。
8. **分页**：`Page{list,total,page,page_size,total_pages}`；page ≥ 1，page_size 钳制 1~100。
9. **参数校验**（dto.rs）：菜名 ≤64 字符；分类 8 种 / 菜系 8 种 / 难度 3 档 / 餐次 4 种 / 订单状态 5 种 / 食材分组 4 种 / 成员角色 3 种；备菜与烹饪时长 0~600 分钟；份数 1~20；就餐人数 1~30；评分 1~5；用量 0~100000；封面渐变必须以 `linear-gradient` 开头；主题色 `#RRGGBB`；备注长度 512/255/1000 分级限制；步骤支持纯字符串或 `{content, duration_sec}` 两种写法（serde untagged）。
10. **订单号生成**：`YYYYMMDD-{B/L/D/S}-{三位序号}`，事务内按当日同餐次订单数 +1。

### 2.3 菜谱模块（recipes.rs）

- **列表**：关键词（菜名/简介/贴士 LIKE）、分类、菜系、难度、标签（EXISTS 子查询）、按成员收藏筛选、含下架选项；5 种排序（评分/最常点/最快/最新/名称）；子查询聚合标签名与收藏数。
- ** facets**：分类/菜系/标签筛选项及各自数量。
- **随机推荐**：`ORDER BY RAND()`，limit 1~12，可按分类。
- **详情**：基础字段 + 创建人昵称 + 标签 + 步骤 + 食材按「主料→辅料→调味料→其他」分组（未知分组追加在后）+ 收藏该菜的成员列表。
- **建档/更新**：事务内写入；食材、标签不存在时**按名称自动建档**（食材默认分类「其他」、emoji 🥬、单位「克」；标签颜色从 10 色调色板循环取）；`tags / ingredients / steps` 三个数组仅在请求中出现时才全量覆盖，便于「只改个名字」。
- **删除**：默认下架（`is_active=0`，历史订单不受影响）；`permanent=true` 物理删除（`order_item.recipe_id` 设 NULL，菜名快照保留）。
- **收藏**：切换式，返回 `favorited`。

### 2.4 订单模块（orders.rs）

- **下单**：明细支持 `recipe_id` 或 `new_recipe`——**顺手建档与入单在同一事务**，前端一次请求完成「现场建新菜 → 加入本单」；逐项校验成员存在、份数钳 1~20；写入菜名快照；`auto_confirm=true` 创建即确认并生成采购清单；返回 `created_recipe_ids`。
- **全流程状态**：草稿 → 已确认 → 烹饪中 → 已开饭 / 已取消；`served` 自动记录 `served_at`。
- **确认订单**：调用存储过程 `sp_confirm_order`，库中无该过程时**自动回退等价原生 SQL**；随后无条件权威重算菜谱统计（幂等）。
- **取消 / 删除订单**：删除前先取涉及菜谱 ID（明细会级联删除，事后无法回退），再重算统计。
- **追加 / 修改 / 删除明细**：已取消订单不可改；`served` 订单不允许删明细（可标记「跳过」）；份数、评分、出菜状态变化自动重算统计与（非草稿）采购清单。
- **餐后评分**：独立便捷端点，返回该菜新的平均分。
- **采购清单**：
  - 草稿单：实时从视图 `v_order_shopping_preview` 计算，**不落库**（确认前随时会变）；
  - 已确认单：读 `shopping_item` 表，保留「已购买」勾选状态；
  - 聚合规则：`合计用量 = Σ(菜谱用量 × 点单份数 ÷ 菜谱默认份数)`，同名同单位跨菜合并，**单位不同分开统计**（土豆 300 克与 2 个不相加），可选配料不进清单；
  - 展示分「需采购（按 13 类固定顺序分组）/ 家中常备（折叠）」；
  - 支持逐项勾选已买、一键清空勾选、按订单增删改自动重算。
- **菜单卡片** `GET /orders/{id}/menu`：供打印/分享；**照单再来** `POST /orders/{id}/reorder`：按历史订单生成新草稿；**这一餐怎么做** `GET /orders/{id}/recipes`：去重保序返回全部菜完整做法（MySQL 不允许 DISTINCT + 未选中列 ORDER BY，改用 `GROUP BY + MIN(sort_order)` 规避 errno 3065）。
- **统计口径**（`refresh_recipe_stats`）：`cook_count` = 有效订单总份数，`avg_rating` = 有效订单非空评分均值，排除草稿/已取消/skipped；**全量重算而非 +1/-1 增量**，任何增删改路径都收敛到真实值。

### 2.5 基础字典模块（basics.rs）

- **成员**：增删改查；删除时有历史订单的成员自动转为停用（避免外键悬空）；角色 admin/member/child。
- **食材**：分页 + 关键词 + 分类 + 常备/需采购筛选，按 13 类固定顺序；删除时被菜谱引用的自动停用（外键 RESTRICT）。
- **标签**：列表带引用菜谱数；增删。

### 2.6 统计模块（stats.rs）

- **首页概览**：菜谱总数/上架数、成员数、食材数、订单总数/今日/待处理、累计上菜、平均评分、点得最多的分类、全家最爱菜品。
- **人气排行**：limit 1~50，支持按分类、按最近 N 天。
- **分类分布**：每分类的菜谱数 + 点单数。
- **全家口味排行**：每位成员的点单数、总份数、平均分、最近点餐日、最爱分类、常点 top3。
- **成员口味画像**：汇总、分类偏好（次数+均分）、常点 top5、收藏 top10。
- **月历**：指定年月的每日订单数与当天菜品名聚合。
- **智能推荐**（「今晚吃什么」）：优先推最近 N 天（默认 7）没吃过的 → 候选按 `avg_rating×2 + cook_count` 加权 → 按荤素汤搭配取 2 个家常菜/主食 + 1 个凉菜 + 1 个汤羹，不足再补齐；候选为空（最近天天点同样的菜）退化为纯随机。

### 2.7 封面图片上传（uploads.rs）

- `POST /api/uploads`：接收 JSON `{data}`（dataURL 或纯 base64），**手写 base64 解码**（不引额外依赖）；先按字符数粗限再解码校验；解码后上限 1.4MB；**按文件魔数**识别 JPG/PNG/GIF/WebP（不信客户端声明的类型）；文件名「时间戳-序号-纳秒.扩展名」落盘 `UPLOAD_DIR`（默认 `./uploads`），返回 `/api/uploads/{name}` 相对地址可直接存入 `recipe.cover_url`。
- `GET /api/uploads/{name}`：文件名白名单校验（防路径穿越），按扩展名返回 Content-Type，`Cache-Control: max-age=31536000, immutable`。

## 三、数据库（database/）

### 3.1 结构（01_schema.sql，517 行）

- **11 张表**：`member`（成员，昵称唯一）、`recipe`（菜谱主表，菜名唯一）、`recipe_step`（步骤，可记单步耗时）、`ingredient`（食材字典，`is_staple` 标家中常备）、`recipe_ingredient`（用量，基于默认份数）、`tag` / `recipe_tag`（标签多对多）、`member_favorite`（收藏）、`meal_order`（一餐一单，订单号唯一）、`order_item`（明细，**菜名快照**）、`shopping_item`（采购清单，含勾选状态）。
- **5 个视图**：`v_recipe_full`（菜谱+各子表数量）、`v_order_detail`、`v_order_shopping_preview`（**核心**：份数换算+跨菜合并+单位隔离）、`v_member_taste_stat`、`v_category_stat`（窗口函数 `ROW_NUMBER` 做分类内排名）。
- **2 个存储过程**：`sp_generate_shopping_list`（幂等先删后插，订单不存在抛 45000）、`sp_confirm_order`（`FOR UPDATE` 锁行 → 确认 → 按明细重算统计 → 生成采购清单，单事务）。
- **约束与索引**：14 个外键（RESTRICT / SET NULL / CASCADE 按业务语义分别设计）、15 个 CHECK（难度、餐次、状态、评分 1-5、份数、颜色正则、用量区间）、29 个索引，含 **ngram 全文索引**（中文菜名/简介搜索）。
- **生成列** `recipe.total_minutes = prep + cook`（STORED）；备份导出时按 `GENERATION_EXPRESSION` 判定并排除生成列（避免 `ER_NON_DEFAULT_VALUE_FOR_GENERATED_COLUMN`，且不误伤 `DEFAULT_GENERATED` 时间戳）。
- 可选定时事件 `ev_refresh_recipe_rating`（默认注释，需 `event_scheduler=ON`）。

### 3.2 种子数据（02_seed_data.sql）

5 位成员（爸爸/妈妈/哥哥/妹妹/奶奶，各带口味备注）、10 个标签、88 种食材、30 道菜谱（含步骤与用量）、4 笔历史订单 + 自动生成的采购清单；主键全部显式指定、TRUNCATE 后插入，可重复执行。

## 四、前端功能点（Vue 3）

### 4.1 基础设施

- **HTTP 层**（api/http.js）：axios 封装，统一 `{code,message,data}` 解包；错误按 503/404/5xx/网络分类给出中文文案。
- **在线探测与降级**（api/index.js）：首次探测后确定 online 标志并广播；在线请求遇 503/网络错误自动切 Mock；`VITE_FORCE_MOCK=true` 可强制演示模式。
- **Mock 层**（api/mock.js，304 行）：15 道示例菜谱、5 成员、10 标签、4 笔订单；`computeShoppingList` **在前端复刻数据库视图的聚合逻辑**（份数换算、同名同单位合并、常备折叠）；订单/菜谱/成员的增删改查全部有内存实现。
- **路由**：18 条；5 个 tab 页 keep-alive 保滚动位置；`afterEach` 设置文档标题。
- **全局**：Toast 提示（success/error/info/warn 四类，不引第三方库）、页面切换动画、离线提示条、全局错误兜底防白屏。
- **图片压缩**（utils/image.js）：`createImageBitmap`（自动应用 EXIF 方向）→ 等比缩到 1080px → JPEG 0.85，典型产物 100~300KB，匹配后端解码上限；旧浏览器回退 `<img>` 方式。

### 4.2 页面清单（按底部导航 + 二级页）

**1. 首页（HomeView）**
- 按时段问候语 + 当前成员头像（点击跳成员切换）。
- 顶部横向自动轮播卡（4 秒间隔、圆点指示、触摸暂停），有数据才占位：
  - 健康提醒（经期/排卵，按紧急度排序，点击进提醒页）；
  - 快递代取（全家待取件，按收件人分组、每人最多露 2 个取件码、超时计数）；
  - 今日厨房语录（12 条池按日期确定性选取）；
  - 今天推荐（智能推荐首位，一键加入点餐单）；
  - 家的账本（上架菜数/点餐次数/平均评分）；
  - 常点榜第一。
- 今日安排：今日三餐订单卡片（餐次 emoji、菜品 emoji 串、状态、道数人数）。
- 猜你想吃：智能推荐横滑，支持「换一批」。
- 快速入口：开始点餐（带购物车角标）/ 菜谱库 / 记一道菜 / 家的味道。
- 家常榜单 top5：评分星级、点过次数、一键加入。

**2. 菜谱库（RecipeListView）**
- 搜索框（320ms 防抖）、分类横滑 chips（带数量）、5 种排序下拉（评分最高/最常点/最快做/最新加/按名称）。
- 无限滚动加载、骨架屏、空态引导新建、悬浮「＋」新建按钮；网格列数随屏宽 2/3/4 自适应。

**3. 菜谱详情（RecipeDetailView）**
- Hero 封面：`cover_url` 真实图片（加载失败自动回退 emoji + 渐变）。
- 标题卡（负边距叠层）：菜名、收藏按钮、简介、标签 chips、评分/难度/分类/菜系。
- 四项统计：总耗时、默认份量、千卡/份、点过次数。
- 食材用量：Stepper 调份数（1-20）**实时换算**全部用量；按主料/辅料/调味料/其他分组；可选配料标记。
- 做法步骤（含单步耗时）、小贴士、记录人与食材种数。
- 底部操作栏：收藏 / 编辑 / 下架（二次确认）/ 加入点餐单。

**4. 菜谱编辑（RecipeEditView）**
- 新建、编辑、点餐页「顺手建档」三用（`?from=cart` 时保存后自动加回购物车）。
- 基础信息：名称、分类、菜系、难度、备菜/烹饪时长、份数、热量、简介、贴士。

## 五、工程实现亮点（值得记录的决策）

1. **顺手建档同事务**：点餐时菜谱库没有的菜，后端在同一事务内先建菜谱再加入订单，前端一次请求，不会出现「菜建了单没成」的中间态。
2. **统计权威重算而非增量**：确认/取消/删除订单、改明细、评分等所有路径统一走 `refresh_recipe_stats` 按明细全量重算，根治了增量方案「cook_count 只增不减、avg_rating 被已删订单污染」的漂移问题（数据库侧还有 `fix-stats.mjs` 做历史数据修复）。
3. **采购清单三重正确性**：按份数换算、同名同单位合并而**单位不同不相加**、可选配料不进清单；草稿单实时算（视图）、确认后落库保留勾选状态。
4. **菜名/食材名快照**：菜谱改名或删除后，历史订单与采购清单依然可追溯。
5. **存储过程缺失自动回退**：只导部分脚本的库也能正常确认订单。
6. **前后端双重离线保障**：后端无库时返回带引导的 503；前端自动切 Mock 且 Mock 复刻了视图级聚合逻辑，演示效果与线上一致。
7. **上传安全**：魔数校验真实格式、文件名白名单防穿越、immutable 缓存、前端预压缩。
8. **SQL 注入防护**：动态条件一律 `QueryBuilder` 绑定参数，杜绝「条件个数与绑定顺序错位」类 bug。
9. **MySQL 版本陷阱处理**：`DISTINCT` + 未选中列 `ORDER BY`（errno 3065）改用 `GROUP BY + MIN(sort_order)`；生成列判定用 `GENERATION_EXPRESSION` 而非 `EXTTA LIKE '%GENERATED%'`。
10. **快递100 预留**：取件码已存运单号与公司 `com` 编码，后端配置项就绪，后期接物流轨迹无需改数据模型。
